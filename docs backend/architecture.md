# Архитектура платформы удалённых лабораторных по ПЛИС

Версия 1.0 · 9 октября 2026 года

## 1 Общая архитектура

Платформа позволяет студенту написать Verilog-код в браузере, отправить его на проверку и получить результат выполнения на плате Terasic C5G. Бэкенд отвечает за пользователей, права доступа, лабораторные, очередь и хранение результатов. Работа с Quartus, прошивкой и UART выполняется отдельным модулем стенда.

Предлагается модульный монолит: один бэкенд с разделением по задачам и отдельный процесс worker для длительных проверок. Оба процесса используют общую базу данных. Для одной платы этого достаточно; микросервисы в MVP не требуются. Документ описывает план реализации, а не уже готовые функции.

### Компоненты

| Компонент | Назначение |
|---|---|
| Фронтенд | React, TypeScript, Vite и Fluent UI; страницы, формы, редактор и модель платы |
| HTTP API | FastAPI; вход, права доступа, лабораторные, отправка работ и выдача результатов |
| База данных | PostgreSQL; пользователи, задания, попытки, очередь и результаты |
| Worker | Отдельный Python-процесс; получение заданий из БД и взаимодействие со стендом |
| Адаптер стенда | Локальные операции или SSH/SFTP; единый интерфейс для worker |
| Стенд | fpga-dispatch, внутренний fpga-run, Quartus и реальная плата |

Фронтенд обращается только к HTTP API. API записывает работу в БД и возвращает идентификатор попытки. Worker забирает её из очереди, передаёт на стенд, получает прогресс и результат. API отдаёт фронтенду сохранённые данные. Браузер не обращается к стенду напрямую.

### Границы MVP

Первый этап включает вход с двумя ролями, две готовые лабораторные, отправку Verilog-2001, очередь, прогресс, результаты и демонстрационный пример. Одна плата выполняет одну проверку одновременно. Кабинет преподавателя, приглашения и просмотр истории добавляются на втором этапе. Создание лабораторных через интерфейс и новые HDL-языки относятся к расширениям.

### Разделение работы

Бэкендер 1 отвечает за общую структуру, конфигурацию, пользователей, регистрацию, вход и проверки прав. Бэкендер 2 — за лабораторные, попытки, очередь и адаптер стенда. Схему БД, API и миграции согласуют оба разработчика. Это предлагаемое разделение; конкретные задачи закрепляются командой. Фронтенд реализует интерфейс, специалист по ПЛИС — исполнитель стенда, аналитик — требования и тестовые наборы.

## 2 Структура бэкенда

Бэкенд размещается в src/backend рядом с существующими src/frontend и src/fpga. Папки фронтенда assets, theme, components и pages сохраняются в его части проекта. Внутри бэкенда предлагается следующая структура.

| app/core/security.py | Хеширование паролей, работа с сессиями |
| app/core/permissions.py | Проверки ролей и доступа к объектам |
| app/db/session.py | Подключение к PostgreSQL и транзакции |
| app/db/base.py | Общая база моделей SQLAlchemy |
| app/modules/auth/ | Регистрация, вход, выход и текущий пользователь |
| app/modules/users/ | Пользователи и их профили |
| app/modules/labs/ | Описание работ, шаблоны и открытые примеры |
| app/modules/groups/ | Группы и приглашения, этап 2 |

| app/modules/submissions/ | Отправленные решения и доступ к результатам |

| app/integrations/fpga/ | client.py, local.py, ssh.py и schemas.py |

В корне репозитория: compose.yaml для API, worker и PostgreSQL; docs/architecture.md для этого документа. Реальные пароли, ключи и .env в Git не добавляются.

### Устройство модуля

В каждом предметном модуле используются router.py для HTTP-маршрутов, schemas.py для входных и выходных данных, service.py для бизнес-правил, repository.py для запросов к БД и models.py для таблиц. Создаются только файлы, нужные конкретному модулю.

Направление вызовов: router вызывает service, service обращается к repository, repository работает с БД. Маршрут не запускает Quartus и не содержит длительный цикл опроса. Правила доступа проверяются на сервере, независимо от видимости кнопок на сайте.

## 3 Модель данных

Используются UUID как идентификаторы и время в UTC. Изменения схемы оформляются миграциями. Ниже перечислены основные таблицы; точные типы и дополнительные индексы определяются при реализации.

| Таблица | Основные поля и связи |
|---|---|
| users | id, email, full_name, role, password_hash, is_active, created_at; email уникален |
| external_identities | id, user_id, provider, subject; уникальная пара provider и subject для TPU ID |
| sessions | id, user_id, token_hash, expires_at, revoked_at; серверные сессии |
| labs | id, title, description, template_code, kind, test_set, test_set_version, is_active |
| submissions | id, user_id, lab_id, source_code, state, created_at, completed_at |
| runs | id = run_id стенда, submission_id, mode, state, stage, result_status, hardware_verified, timestamps, result_json |
| artifacts | id, run_id, kind, storage_key, size_bytes; исходники и необходимые логи |
| user_limits | user_id, next_allowed_at; ограничение аппаратных отправок |
| groups | id, teacher_id, name; этап 2 |
| group_members | group_id, student_id; уникальная пара, этап 2 |
| assignments | id, group_id, lab_id, deadline; этап 2 |
| invitations | id, group_id, token_hash, expires_at, revoked_at; этап 2 |

Пользователь имеет несколько отправленных решений. Лабораторная связана с несколькими решениями. Одно решение может иметь несколько исполнений на стенде: например, первое завершилось busy, после чего worker создал новый run_id. Технический повтор не увеличивает число студенческих отправок.

### Состояния решения и исполнения

submissions.state отражает состояние пользовательской работы: queued, processing или completed. runs.state и runs.stage сохраняют состояние конкретного исполнения по контракту стенда. Итог runs.result_status хранится отдельно: passed, mismatch, build_error, board_error, invalid_input, busy или internal_error.

Состояние finished у стенда не равно успешной сдаче. hardware_verified может быть true при mismatch: аппаратные измерения получены, но ответы неверны. Потеря связи записывается как состояние связи, а итог не подменяется предположением.

### Хранение и открытые данные

Очередь хранится в PostgreSQL, поэтому не исчезает после перезапуска API. Для крупных логов используется постоянный каталог с метаданными в artifacts; содержимое каталога не публикуется как общедоступная статика. JSON результата хранится в служебной части БД. В публичный ответ включаются только разрешённые поля и открытые наблюдения.

Предлагаемое расширение контракта: каждому вектору назначить признак public или hidden в доверенных метаданных тестового набора. Сейчас контракт содержит vector_index, но не признак видимости. До согласования worker не выдаёт массив observations студенту целиком. Скрытые входы, эталоны и служебные логи не должны попадать в доступные студенту ответы.

## 4 Вход и HTTP API

Основной вариант — вход через TPU ID, если университет предоставит регистрацию приложения и параметры интеграции. После подтверждения личности сервер находит или создаёт локального пользователя. Наличие кнопки TPU ID на фронтенде не означает, что подключение уже работает. Протокол и набор данных уточняются у ТПУ.

Резервный вариант пилота — собственный вход по email и паролю. Пароль хранится только как хеш Argon2id. Самостоятельная регистрация создаёт студента; преподаватель назначается администратором через служебную команду. Поле роли из формы регистрации не принимается как основание для повышения прав.

Для браузера предлагается серверная сессия с непрозрачным случайным токеном в HttpOnly cookie. В БД хранится хеш токена; выход отзывает сессию. В развёрнутой системе включаются HTTPS и Secure cookie, защита изменяющих запросов от CSRF, проверка Origin и явный список разрешённых источников. Срок сессии задаётся настройкой. Для внешнего входа также проверяется привязка callback к начатому запросу входа по правилам выбранного протокола.

### Предлагаемые маршруты

Все пути имеют префикс /api/v1. Пути внешнего входа уточняются после согласования TPU ID.

| Метод и путь | Назначение |
|---|---|
| POST /auth/register | Создать студента, если включена собственная регистрация |
| POST /auth/login | Проверить email и пароль, создать сессию |
| POST /auth/logout | Отозвать текущую сессию |
| GET /auth/me | Вернуть профиль и роль текущего пользователя |
| GET /auth/tpu/login | Начать внешний вход |
| GET /auth/tpu/callback | Обработать ответ системы входа ТПУ |
| GET /labs и GET /labs/{id} | Список доступных работ и описание работы |
| GET /labs/{id}/example | Готовые данные примера, без кода эталонного решения |
| POST /labs/{id}/submissions | Принять HDL-код, вернуть 202 и submission_id |
| GET /submissions/{id} | Прогресс, итог и разрешённые наблюдения |
| GET /submissions/{id}/logs | Только подготовленные для пользователя логи |
| GET /health | Проверка доступности API, без секретных настроек |

На втором этапе добавляются маршруты групп, приглашений, назначений и истории. Студент получает только собственные работы; преподаватель — работы студентов своих групп. Для MVP доступные лабораторные задаются заранее, до появления полноценного механизма назначений.

Повтор POST с одинаковым Idempotency-Key от одного пользователя возвращает ранее созданную отправку; ключ с другим содержимым отклоняется. Ошибки: 401 — нет действующего входа, 403 — недостаточно прав, 422 — неверный формат, 429 — интервал отправок не истёк. Фронтенд получает retry_after или next_allowed_at. Проверку прогресса MVP выполняет периодическими GET; WebSocket можно добавить позже.

## 5 Очередь и интеграция со стендом

1. API проверяет сессию, доступ к лабораторной, размер кода и допустимый формат. В одной транзакции блокируется запись лимита пользователя, проверяется интервал и создаётся submission со state = queued. Это предотвращает две одновременные отправки в обход ограничения.
2. Worker выбирает старейшую работу из очереди. Для MVP запускается один worker; дополнительно блокировка в PostgreSQL защищает от запуска второго обработчика. При потере блокировки или связи с БД новые исполнения не отправляются.
3. Worker сохраняет run_id до внешнего вызова, создаёт incoming/<run_id>, исходник src/student_top.v и manifest.json. Поля top, kind и test_set берутся из настроек лабораторной. Студент передаёт только HDL-код.
4. После полной загрузки вызывается fpga-dispatch submit --run-id <UUID> --mode hardware. Адаптер реализует те же операции локально либо по SFTP/SSH. Пользовательские строки не подставляются в shell-команды; UUID и допустимые параметры проверяются.
5. Worker вызывает fpga-dispatch status и сохраняет прогресс в БД. accepted означает регистрацию исполнения, а не успешную сборку. HTTP-запрос студента не ждёт окончания проверки.
6. При finished worker получает result.json и разрешённые логи, проверяет schema_version, run_id, mode, структуру и пути артефактов. Результат сохраняется до вызова cleanup. Успешная очистка фиксируется отдельно; её повтор не запускает работу заново.

### Повторы и восстановление

| Ситуация | Действие бэкенда |
|---|---|
| busy | Сохранить завершённый run; вернуть submission в очередь; позднее создать новый run_id |
| Ответ submit потерян | Проверить тот же run_id через status; не создавать новый запуск вслепую |
| Перезапуск worker | Восстановить незавершённые runs из БД и запросить их состояние |
| Стенд недоступен | Показать отсутствие связи; повторить получение состояния после восстановления |
| finished без результата | Повторно запросить диспетчер; не выставлять passed |
| board_error или internal_error | Сохранить инфраструктурный итог; автоматический аппаратный повтор не выполнять |
| cleanup не удался | Сохранённый результат оставить доступным; повторять только очистку |

Планируемый интервал отправок — настройка в пределах 5–10 минут; точное значение и момент отсчёта согласуются командой. Предлагается считать его от принятия отправки. busy относится к тому же submission и не расходует новую попытку. После board_error/internal_error ограничение снимается для повторной отправки, если после этой работы пользователь не создал более новую; изменение выполняется транзакционно.

### Демонстрация и безопасность

Кнопка примера получает заранее подготовленные открытые данные; аппаратная очередь не используется. Если демонстрация реализуется через fpga-dispatch mock, она имеет отдельное исполнение и всегда hardware_verified = false. Автоматического переключения с hardware на mock нет.

API не принимает .sof, настройки пинов, команды, пути стенда и эталоны. Ограничения ресурсов и проверка HDL реализуются также на стенде: проверка HTTP-входа не заменяет изоляцию сборки. Точный процент готовности и оставшееся время не обещаются.

## 6 Развёртывание и порядок реализации

### Размещение процессов

На сервере приложения работают фронтенд, HTTP API, worker и PostgreSQL. API и worker запускаются из одного образа разными командами. Пользовательские данные и артефакты размещаются в постоянных томах. Входящие соединения принимает HTTPS-прокси; PostgreSQL и служебные каталоги не публикуются наружу.

Quartus и fpga-dispatch работают на машине с платой. Предпочтительный путь при разных машинах — SSH/SFTP с отдельной служебной учётной записью, ключом и проверкой ключа хоста. Для общего компьютера включается локальный адаптер. Доступ к USB и Quartus контейнеру HTTP API не нужен. Исполнитель стенда запускается независимо через systemd, как предусмотрено контрактом.

Для MVP очередь реализуется в PostgreSQL. Redis и Celery не вводятся без необходимости; их можно добавить при изменении требований. WebSocket также не обязателен для первого этапа. Стек README при согласовании следует привести к выбранной реализации, чтобы он не перечислял одновременно альтернативные фреймворки.

### Порядок реализации

| Шаг | Результат |
|---|---|
| 1 | Согласованные FastAPI, способ входа, структура модулей и границы двух бэкендеров |
| 2 | Запуск API и PostgreSQL, конфигурация, первые миграции и /health |
| 3 | Пользователи, вход, выход, сессии и серверные проверки ролей |
| 4 | Две лабораторные, шаблоны, открытые примеры и согласованные ответы фронтенду |
| 5 | Приём кода, идемпотентность, лимит отправок и постоянная очередь |
| 6 | Worker и адаптер, обработка статусов, результатов, ошибок и очистки |
| 7 | Проверка на реальной плате и демонстрационный сценарий MVP |
| 8 | Группы, приглашения, назначения и пользовательская история, этап 2 |

### Проверки перед демонстрацией

Проверяются успешный и неверный вход, запрет самостоятельного получения роли преподавателя, отказ в доступе к чужому submission, одновременные отправки и лимит частоты. Для worker проверяются busy, потерянный ответ submit, перезапуск, отсутствие связи, ошибка платы и повтор очистки. Отдельно проверяется, что скрытые векторы, эталоны и эталонный HDL-код отсутствуют в доступных студенту ответах и логах.

### Решения для согласования

До реализации уточняются доступность TPU ID, порядок выдачи роли преподавателя, интервал аппаратных попыток и его поведение при сбоях. Со специалистом по ПЛИС согласуются видимость векторов, формат безопасных логов, HDL-интерфейс, test_set и его версия. В контракте manifest сейчас нет версии test_set: предлагается использовать неизменяемые имена наборов либо добавить поле версии. Параметры времени сборки и ограничения ресурсов определяются по измерениям стенда.
